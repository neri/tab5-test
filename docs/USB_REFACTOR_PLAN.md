## 背景・目的

[`USB_HOST_PLAN.md`](USB_HOST_PLAN.md)（HID Bootキーボード、Stage 4でハブ対応）と
[`USB_MSC_PLAN.md`](USB_MSC_PLAN.md)（USBメモリ、直結のみ）は、どちらも
「1機能=1マイルストーン」の方針どおり**常に1台のデバイスだけを相手にする**
前提で組まれている。実機で使えるようになった結果、次の課題が表面化した。

- **挿す順番でHIDが認識できないことがある**: ハブの複数ポートに機器を挿すと、
  `hub::Hub::find_connected_port`は「見つかった最初の1ポート」しか選ばない
  （`src/usb/hub.rs:389`）。ポート番号の若い方が優先されるため、後から挿した
  デバイスや2台目以降は最初から列挙すらされない
- **USBメモリをハブ経由で挿しても認識できない**: `usbmsc`/`usbread`/`usbmbr`は
  `usb::enumerate_device(usb::ROOT_DEVICE_ADDRESS, false)`をUSB-A直結決め打ちで
  呼んでおり（`USB_MSC_PLAN.md`「範囲外」節に明記の既知の制限）、
  `connect_keyboard`に相当するハブ経由判定が無い
- **複数デバイスを同時に使うことがそもそも想定されていない**: デバイスアドレスは
  「ハブ=1、ハブ配下の1台=2」に完全固定（`src/usb/protocol.rs:24-31`）。
  ハブに複数台挿しても2台目以降は住所を持てない。加えて`hcd.rs`はチャネル0を
  1つしか使わない設計で、`lcd.rs`が保持するのも`Option<UsbKeyboard>`1個だけ
  （`src/lcd.rs:141`）

このリファクタの目的は、**ハブ1段（可能ならそれ以上）にぶら下がる全ポートを
把握し、挿す順番に関係なく全デバイスがそれぞれ正しく動く**状態にすること、
および**USB MSCをハブ経由でも使えるようにする**ことの2点。

## リファクタ着手時点の制約（実装調査のまとめ）

リファクタの前提として、当時の実装が「なぜ複数デバイスを扱えないか」を
コードの箇所付きで整理したもの。**この表と直前の「背景・目的」は着手時点の
記録であり、現在の状態ではない**（行番号も当時のもの）。各制約が解消された
Stageは以降の節を参照。

| 制約 | 場所 | 内容 |
|---|---|---|
| デバイスアドレス固定2枠 | `protocol.rs:24-31` `ROOT_DEVICE_ADDRESS=1` `DOWNSTREAM_DEVICE_ADDRESS=2` | 動的アドレスプールが無く、ハブ配下は1台しか住所を持てない |
| ハブは1ポートしか選ばない | `hub.rs:378-427` `find_connected_port` | 「見つかった最初のremovableポート」のみを返す。他ポートの接続は無視される |
| ハブのホットプラグ検出なし | `hid_keyboard.rs:198-210` `is_connected`のdocコメント | ルートの`HPRT`しか見ないため、ハブのポート単位の抜き差しは`needs_reinit`（エラー連続10回）経由の間接検知のみ |
| チャネルはハードウェア上0番のみ | `hcd.rs:214-218` | チャネルアロケータが無く、同時に扱える転送は1つ。ただし「毎回状態を持たず1パケット分書き切ってpollする」設計自体は複数デバイスの**逐次**ポーリングと矛盾しない（後述） |
| USB全体のオーナーが1つに定まっていない | `hid_keyboard.rs:216-224`、`USB_HOST_PLAN.md`「踏んだ罠その2」 | `lcd.rs`のフレームループと`usbinfo`/`usbvbus`/`usbhub`/`usbmsc`等のシェルコマンドが、それぞれ独立に`probe_port`（コアの完全リセット＋バスリセット）を呼べてしまう。生きているセッションのアドレス/設定状態がバス側でリセットされ食い違う、という既知のバグ（`needs_reinit`の自己回復で救っているが、キーボードだけの対策で他クラスには無い） |
| MSCはハブ経由未対応・レジストリに乗っていない | `USB_MSC_PLAN.md`「範囲外」節 | `connect_mass_storage`相当の関数が無く、シェルコマンドのたびに直結決め打ちで再列挙する使い捨て実装 |
| 多段ハブ非対応 | `hub.rs:9-10` | 「ハブの下のハブ」は最初から範囲外と明記 |
| Split Transaction非対応 | `hcd.rs`のコメント、`USB_HOST_PLAN.md` Stage 4 | このリファクタ当時は`FORCE_FS_LS_ONLY_HOST=true`でホスト自体をFS/LS専用に固定していた。**このリファクタでは変更しない**（別の大きな計画になるため）。→ `USB_HOST_PLAN.md` Stage 6で実装済み。ハードウェアには`HCSPLT`が実在した |

重要な点として、チャネル0しか無いこと自体は「複数デバイスを扱えない」直接の
理由ではない。既存のポーリング方式（`hcd::run_packet`が1パケットごとに
完結し、呼び出し間の状態を持たない）は、**フレームループの中で複数デバイスの
エンドポイントを順番に呼ぶ**分には何も崩れない。実際に崩れているのは
「デバイス管理側」（アドレス割り当て・ポート選択・保持する台数・バスの
所有権）であり、このリファクタはそこに絞る。真の並列転送（フレームリスト＋
チャネルアロケータ＋割り込み駆動）は`USB_HOST_PLAN.md`のStage 5として
既に将来課題化されており、本計画では引き続き対象外とする。

## 方針（設計原則）

1. **USBバスの所有者を1つに一本化する**。`lcd.rs`のフレームループが唯一
   `hcd`/`hub`を直接操作する場所とし、シェルコマンド（`usbinfo`/`usbhub`/
   `usbmsc`等）はバスを新たに叩くのではなく、フレームループが保持している
   デバイスレジストリを覗くだけにする。これで「シェルコマンドが生きている
   セッションを下からリセットする」既知のバグ（`hid_keyboard.rs:216-224`）が
   クラス横断で根本的に解消する
2. **固定2枠のアドレスを、ポート数ぶんの小さな固定長プールに置き換える**。
   `USB_MSC_PLAN.md` Stage 6が示す「タスクが要求する
   以上の抽象化をしない」方針に従い、`Vec`や無制限プールは使わず、
   `hub::MAX_PORTS`と同様に上限（例: ルート1台＋ハブ最大8ポート＝9枠）を
   持つ固定長配列にする
3. **ハブは全ポートを見る**。「最初の1ポート」から「接続されている全ポート」を
   走査する形に変え、挿す順番・ポート番号に関係なく全デバイスを拾う
4. **フレームループのポーリングは1台から複数台のラウンドロビンへ**。
   `hcd::run_packet`のプリミティブ自体は変更せず、呼び出し元
   （レジストリの走査ループ）を1回から複数回に増やすだけにとどめる
5. **クラス非依存のスロット管理と、クラス固有のクラスドライバを分離**
   したまま拡張する。`hid_keyboard.rs`/`hub.rs`/`msc.rs`の役割分担
   （`usb.rs`のモジュールdocに書かれている4層構造）は崩さず、新設する
   「デバイスレジストリ」層はその上に乗る5層目として追加する
6. **多段ハブ（Stage G）は「可能であれば」の努力目標とし、Stage A〜Fが
   実機で安定してから着手する**。手元の検証機材次第では最終的に見送る
   判断もあり得る、と明記しておく

## Stage A: USBバスの単一オーナー化 ✅ 実装完了（実機一部確認）

現状バグ（`hid_keyboard.rs:216-224`）を先に潰しておかないと、以降の
Stageで複数デバイスを保持するようになるほど「シェルコマンドが下から
バスをリセットする」影響範囲が広がってしまうため、最初に着手する。

- 新設: `struct UsbHost`（仮、`usb.rs`直下または新規`src/usb/registry.rs`）。
  `probe_port`/`Hub::open`など、これまで`connect_keyboard`や各シェル
  コマンドがバラバラに呼んでいたバス操作を、この構造体のメソッド経由に
  一本化する
- `lcd.rs`のフレームループが`UsbHost`を1つ所有し、これまでの
  `usb_keyboard: Option<UsbKeyboard>`ローカル変数を`UsbHost`内部の
  レジストリ（Stage Bで詳細化）に置き換える
- `shell.rs`の`usbinfo`/`usbvbus`/`usbhub`/`usbmsc`/`usbread`/`usbmbr`は、
  `UsbHost`への参照を受け取り、**新規にバスを叩く代わりに現在の
  レジストリの中身を表示するだけ**にする。バスへ新規アクセスが必要な
  操作（強制再列挙など）は明示コマンド（例: `usbrescan`）として残し、
  それ以外の通常コマンドは「今何が挿さっているか」を読むだけの
  読み取り専用にする
- ゴール: `usbinfo`をUSBキーボードのポーリング中に実行しても、
  キーボードのセッションが壊れない（`needs_reinit`が発火しない）ことを
  実機で確認する

**設計上の注意**: `shell.rs`のコマンドは`Console`経由で呼ばれ、アプリケーションの
フレームループとは別の実行タイミング（同じシングルスレッドの割り込み
処理の合間ではあるが、呼び出し元が違う）で動く。`UsbHost`を単一の
`static`や`Cell`越しに共有する必要があるか、あるいは`Console`/`shell`
呼び出し自体が`app.rs`のループの中から行われる構造になっているかを
`console.rs`/`shell.rs`の呼び出し経路で確認してから実装方針を決める。

**実装時の判明事項**: `shell::execute`は`app::run`のフレーム
ループから`console.take_submission()`直後に同期呼び出しされているだけで
（`src/app.rs`の`let outcome = shell::execute(console, submission.as_bytes(), &mut usb_host);`）、
別スレッド/別割り込みコンテキストからの呼び出しは無い。つまり懸念していた
「`static`や`RefCell`越しの共有」は不要で、`app.rs`が所有する
`UsbHost`をそのまま`&mut`で`shell::execute`に渡すだけで済んだ。
`shell::execute`のシグネチャに`usb_host: &mut usb::UsbHost`を追加し、
`usbinfo`/`usbrescan`/`usbhub`/`usbmsc`/`usbread`/`usbmbr`の各コマンド
関数へそのまま引き渡している。`usbvbus`はバス状態を一切読まない生の
I2Cビット操作なので変更していない。

`usbinfo`/`usbhub`は完全な読み取り専用コマンドにし、バスを新規に叩く
唯一のコマンドとして`usbrescan`を新設した（計画通り）。ただし`usbhub`の
ポートごとの生ステータス表示だけは例外的に`Hub::port_status`/
`Hub::status`（素のGET_STATUS読み出し）をライブで呼んでいる -- これは
アドレスやコンフィグ状態を一切変更しない読み出し専用リクエストであり、
`rescan`（`probe_port`+`SET_ADDRESS`をやり直す完全リセット）とは性質が
異なるため、Stage Aの「バスをリセットしない」制約には抵触しない。

## Stage B: 動的アドレスプールとデバイススロット ✅ 実機確認済み

- `protocol::ROOT_DEVICE_ADDRESS`/`DOWNSTREAM_DEVICE_ADDRESS`の固定値を
  廃止し、`AddressPool`（内部は`[bool; MAX_DEVICES]`程度の使用中ビット
  マップでよい）に置き換える。ルートポートには従来通りアドレス1を、
  ハブ配下の各ポートにはプールから空いている番号を割り当てる
- `MAX_DEVICES`定数を新設する（例: ルート1台＋ハブ8ポート分＝9。
  `hub::MAX_PORTS=31`ほど大きくする必要はなく、実用上のハブは4〜7ポートが
  大半なので、必要になったら広げる程度の余裕を持たせる）
- デバイス種別を横断できる小さな列挙型を新設する:

  ```rust
  enum DeviceSlot {
      Keyboard(hid_keyboard::UsbKeyboard),
      MassStorage(msc::UsbMassStorage),
      Unsupported, // 列挙はできたがクラスドライバが無い（マウス等）
  }
  ```

  `USB_MSC_PLAN.md` Stage 6が`BlockDevice`列挙型を「使われないなら
  導入しない」として見送った教訓を踏まえ、今回はStage C以降で実際に
  `match`で分岐される（ラウンドロビンポーリング、シェルコマンドの表示）
  ため、導入する妥当性がある
- レジストリは`[Option<(u8, DeviceSlot)>; MAX_DEVICES]`
  （`u8`はどのポート/経路に対応するかの識別子）のような固定長配列に
  持たせ、Stage Aで新設する`UsbHost`が所有する
- ゴール: 単体では観測できる変化が無いため、Stage Cの実装と合わせて
  実機確認する

**実装時の変更点**: `AddressPool`という状態を持つ構造体は導入しなかった。
代わりに`protocol::downstream_address(port: u8) -> u8`（`ROOT_DEVICE_ADDRESS
+ port`）という無状態の関数にした。`rescan`は毎回レジストリを全消去して
作り直す設計（Stage Cで確定）にしたため、「アドレスを確保・解放する」
という状態遷移そのものが発生しない -- ポート番号がそのままアドレスの
決定要因になり、想定される罠に書いた「アドレス再利用のタイミング」問題も
最初から存在しない。`MAX_DEVICES`は`usb::registry::MAX_HUB_PORTS = 8`
として実装した（ルート1枠+ハブ8ポート=9スロット）。

`DeviceSlot`という名前は使わず、`DeviceKind`（`Keyboard`/`MassStorage`の
2値）とした -- `UsbHost`内部の1オプションスロットを指す言葉と、そこに
入っているクラスドライバの種別を指す言葉を分けたほうが読みやすいという
判断。`Unsupported`列挙子は作らず、クラスドライバが見つからない場合は
その場でログを出してスロットを`None`のままにする実装にした（列挙型に
値を持たせるより単純なため）。

## Stage C: ハブの全ポート走査と複数デバイスの同時アタッチ ✅ 実機確認済み

- `hub::Hub::find_connected_port`（1ポートだけ返す）を、
  **接続されている全ポートを返す**`scan_connected_ports`のような
  メソッドに置き換える（既存の`find_connected_port`はそのまま残し、
  内部実装をこの新メソッドの「最初の1件を返す」ラッパーにしても良い。
  Stage Aまでの`connect_keyboard`のような単一デバイス呼び出しが
  残っていれば後方互換になる）
- 新規に接続を検出したポートは、**1つずつ順番に**電源投入済み・
  デバウンス済みの状態からリセット→列挙まで行う。`protocol.rs:124-125`
  の「一度にアドレス0の未割当デバイスは1台まで」という制約
  （`enumerate_device`のdocコメント）はこの逐次処理で自然に守られる。
  並行してリセットを開始しない
- 列挙結果の`device_class`を見て、Stage Bの`DeviceSlot`へ振り分ける
  （`hid_keyboard::find_hid_keyboard`が見つかればKeyboard、
  `msc::find_msc_interface`が見つかればMassStorage、どちらでもなければ
  Unsupportedとしてスロットだけ確保しログに出す）
- 既に埋まっているスロット（同じポート番号に対応するもの）は
  スキップし、空いているポートのみ新規アタッチする。これにより
  「毎フレーム全ポート再列挙」にはならず、**新規に挿された分だけ**
  処理する
- ゴール: 実機でハブの複数ポートに種類の異なるデバイス（例:
  キーボード＋USBメモリ、または2台のキーボード）を同時に挿し、
  挿す順番を入れ替えても全台がレジストリに載ることを`usbinfo`
  （Stage Aで読み取り専用化したもの）で確認する

**踏みそうな罠（実装前メモ）**:
- 複数ポートを順番にリセット・列挙する間、既にアタッチ済みの
  デバイスがポーリングされない時間が延びる。ポートが多いハブでは
  初回接続時にキー入力の取りこぼしが増える可能性があるため、
  「1フレームにつき新規ポート1つまで処理する」など、列挙作業を
  複数フレームに分割することも検討する（`lcd.rs`の300フレーム
  スロットルの精神と同じ、ブロッキング時間を1箇所に集中させない
  工夫）
- `Hub::power_on_all_ports`は既に全ポートへ電源投入している
  （`hub.rs:352`以降）ため、Stage Cで追加の電源シーケンス変更は
  基本的に不要なはず

**実装時の変更点**: `find_connected_port`（1ポート版）は削除し、
`Hub::debounce_connected_port(port) -> Option<bool>`（1ポート分の
接続確認+デバウンスだけを行う、状態を持たない関数）に置き換えた。
`UsbHost::attach_hub`が`1..=port_count`をループしてこれを呼び、
`Some(true)`ならその場で`reset_port`→`enumerate_device`→クラス
ドライバのアタッチまで行う。「1フレームにつき新規ポート1つまで」という
分割処理は実装しなかった -- `rescan`自体が呼び出し元(`lcd.rs`のフレーム
ループ)から見て常に「ブロッキングする1回の操作」である前提は
`connect_keyboard`の頃から変わっておらず、ポート数が増えるほど
1回のブロッキング時間が伸びる点は実機で計測してから要否を判断する
（「想定される罠」参照、未検証のまま持ち越し）。

`hub::MAX_PORTS`（31、ハブ記述子のビットマップ用）とは別に、
`registry::MAX_HUB_PORTS`（8、レジストリのスロット数用）を新設した。
ハブの実ポート数がこれを超える場合は`attach_hub`が超過分をログに
出して打ち切る。

## Stage D: フレームループのラウンドロビン・ポーリング化 ✅ 実装完了（実機一部確認）

- `lcd.rs`のフレームループにある「`usb_keyboard`1個をポーリングする」
  ロジック（`src/lcd.rs:200-227`）を、**レジストリ全スロットを走査して
  それぞれの`poll`を呼ぶ**形に一般化する
- `DeviceSlot::Keyboard`は既存の`UsbKeyboard::poll`をそのまま呼び、
  取得したキーを`Console::push`する（複数キーボードが同時に挿さって
  いれば、CardKBとUSBキーボードが今も共存しているのと同じ要領で
  両方の入力が合流する）
- `DeviceSlot::MassStorage`はフレームごとに能動的にポーリングする
  必要はない（HIDのInterrupt INのような「変化を待つ」デバイスでは
  ないため）。`is_connected`相当の生存確認だけをフレームループ内の
  軽い頻度で行い、実際のブロック読み出しはStage Fでシェルコマンドが
  レジストリ越しに要求したときにだけ行う
- 各スロットの`is_connected`/`needs_reinit`判定は`UsbKeyboard`の
  既存パターン（`hid_keyboard.rs:198-227`）をそのままなぞり、
  スロットが死んだら`None`に戻して次回のポート走査（Stage E）で
  再アタッチされるのを待つ
- ゴール: 実機で複数デバイス（例: 直結キーボード＋ハブ経由キーボード、
  あるいはハブの2ポートに挿した2台のキーボード）を同時に操作し、
  両方の入力がコンソールへ正しくエコーされることを確認する

**踏みそうな罠（実装前メモ）**:
- スロット数が増えるほど1フレームあたりのポーリング時間が伸びる。
  `INTERRUPT_POLL_TIMEOUT_ITERATIONS`（現行50,000）はデバイスが
  NAKし続ける場合の待ち時間見積もりなので、複数デバイス分を
  毎フレーム律儀に処理するとアイドル時でもフレーム落ちしうる。
  実機で計測し、必要なら「1フレームにつきポーリングするスロットを
  1〜2個だけ回す」ラウンドロビン（全スロットを数フレームに分けて
  巡回）に落とす

**実装時の変更点**: `UsbHost::poll_keyboards`は全`DeviceKind::Keyboard`
スロットを順番に見て、最初に新しいキーが取れたスロットのバイトを返す
（複数キーボードが同時に打鍵した場合、次のフレームで残りが拾われる）。
「1フレームにつき1〜2スロットだけ回す」間引きは実装しなかった --
実機での計測が先という判断は変えていないので、まずは全スロット毎フレーム
処理する素直な実装のまま実機確認へ進み、フレーム落ちが実測されたら
間引きを追加する。

`DeviceKind::MassStorage`は毎フレームのポーリング対象に含めていない
（計画通り）。生存確認も専用には実装しておらず、Stage Aで導入した
`root_disconnected`（ルートポート1回読みで registry 全体を落とす）と
`needs_reinit`（キーボードのエラーストリークのみが対象）に相乗りする形
になっている -- 詳細は次のStage Eの節を参照。

## Stage E: ハブポート単位のホットプラグ検出（実装しないことにした）

計画時点では「専用の軽量スイープ」を新設する想定だったが、Stage A〜Dを
実装した結果、次の理由でこの計画通りには実装しなかった。

- `rescan`自体が「レジストリを全部消して作り直す」設計（Stage Cのゴール
  達成のため必然的にそうなった -- バスリセットは全デバイスのアドレスを
  一度に無効化するので、1ポートだけを部分更新する経路がそもそも作れない）
  になったため、「ある1ポートの抜去だけを検知してそのスロットだけ
  `None`にする」という計画時点の想定自体が、実装した`rescan`のセマンティクス
  と整合しない。抜去を検知したら、結局`rescan`で全部作り直すことになる
- キーボードスロットについては、`UsbKeyboard::needs_reinit`（エラー
  ストリーク、既存の仕組みをそのまま流用）が、ハブポートから抜かれた
  ことを数フレーム以内に間接検知し、`lcd.rs`が即座に`rescan`する
  （Stage Dの実装のとおり）。これは計画が「間接検知」と呼んでいたものと
  同じで、追加の専用スイープが無くても十分に速い
- 空きポートの検知（新規に何か挿された）は、既存の`has_room`ベースの
  約5秒スロットル（`usb_reconnect_frames == 300`）による定期`rescan`で
  カバーされる。計画が言っていた「専用スイープ」と実質的に同じ役割を、
  新しいコードを足さずに`rescan`の再利用だけで果たしている

**残る既知のギャップ**（実装しないことにした結果、埋まっていない穴）:
USB MSCスロットには`needs_reinit`に相当する「毎フレーム動いていて
エラーを検知できる」仕組みが無い（Stage Dの実装ノート参照）。そのため
ハブポートに挿さったUSBメモリだけを黙って抜いた場合、他の要因
（キーボードのエラー、ルートポート自体の抜去、`usbrescan`の手動実行）が
`rescan`を引き起こすまで、レジストリはそのMSCスロットを「まだ挿さっている」
ものとして持ち続ける。次にそのスロットへ`usbmsc`/`usbread`/`usbmbr`を
実行すると、Bulk転送がタイムアウトして失敗するだけで、クラッシュはしない
（`USB_MSC_PLAN.md`の既存の「MSCに自己回復の作り込みは無い」という
スコープ外項目のまま）。専用のMSC生存確認スイープを追加すれば埋まるが、
優先度は低いと判断し、この計画では見送った。

## Stage F: USB MSCのハブ対応とシェルコマンドのレジストリ統合 ✅ 実装完了（実機一部確認）

- Stage B〜Cの結果、MSCデバイスもハブ配下で列挙されれば自動的に
  `DeviceSlot::MassStorage`としてレジストリに載るようになる。
  `connect_keyboard`が担っていた「直結かハブ経由かを一手に判断する」
  役割は、Stage Cの全ポート走査に吸収されるため、
  `connect_mass_storage`という専用関数を新たに書く必要は無くなる
  見込み（`USB_HOST_PLAN.md`のconnect_keyboardのような1関数構成は
  この計画で自然に解消される）
- `shell.rs`の`usbmsc`/`usbread`/`usbmbr`を、Stage Aの方針どおり
  「新規にバスを叩いて列挙し直す」実装から「レジストリの中から
  `DeviceSlot::MassStorage`を探して使う」実装に置き換える。
  複数のMSCデバイスが挿さっている場合にどれを対象にするかは、
  まず「レジストリ中最初に見つかったMassStorageスロット」で
  十分とし、複数MSC同時操作用の引数（例: `usbread <slot> <lba>`）は
  必要になった時点で追加する
- `wait_until_ready`（`msc.rs`の既存実装）はコマンド単位で呼ぶ現行の
  挙動のまま流用できる。トグル状態（`in_toggle`/`out_toggle`）は
  スロットの`UsbMassStorage`インスタンスに引き続き保持されるため、
  レジストリ化してもデータ化けの心配は増えない
- ゴール: 実機でハブ経由のUSBメモリに対して`usbmsc`/`usbread`/`usbmbr`
  が直結時と同じ結果を返すことを確認する。あわせて、同じハブの
  別ポートにキーボードを挿した状態でも両方が正しく動作すること
  （Stage Dのゴールとの複合確認）を確認する

**実装時の変更点**: `connect_mass_storage`のような専用関数は書かなかった
（計画の見込みどおり、Stage Cの全ポート走査に吸収された）。`usbmsc`/
`usbread`/`usbmbr`は`UsbHost::mass_storage_mut()`（レジストリ中最初に
見つかった`MassStorage`スロットへの`&mut`を返す）を呼ぶだけの薄い実装に
なった。複数MSC同時操作用の引数は計画通り見送った。

`usbmsc`の出力からVID/PID・Bulkエンドポイントアドレスの表示は削除した
-- それらは列挙時にしか分からない情報で、`UsbMassStorage`は
アタッチ後の状態（アドレス・トグルなど）しか保持していないため、
コマンド実行のたびに表示し直すには`EnumeratedDevice`をレジストリ側で
保持し続ける必要があった。かわりに`DeviceSummary`（VID/PID/class/
インターフェース数/config bytes、`Copy`な小さい構造体）をアタッチ時に
1つだけレジストリへ保存し、`usbinfo`/`usbhub`がそれを表示する形にした。
`usbmsc`はSCSIコマンドの結果表示に専念し、識別情報は`usbinfo`を見る
よう案内する（利用者に一手間増えるが、レジストリの保持データを
`EnumeratedDevice`丸ごとから`DeviceSummary`だけに削れたトレードオフ）。

## 想定される罠（実装前メモ、実機で要検証）

- **列挙作業のブロッキング時間**: Stage Cで複数ポートを1回のスイープで
  列挙すると、ポート数分のリセット・列挙（それぞれ数十〜百ms級）が
  直列に積み重なる。既存の「フル列挙は数百msのブロッキング処理」という
  制約（`lcd.rs`の300フレームスロットルの理由）が、ポート数倍に
  膨らむ可能性がある。フレーム単位での分割処理（Stage Cの罠メモ参照）が
  実機で本当に必要か測って判断する
- **アドレス再利用のタイミング**: → Stage Bの実装時の変更点で解消済み。
  アドレスをポート番号から毎回計算する無状態設計にしたため、
  「解放してから再利用する」という操作自体が存在しない
- **シェルコマンドとフレームループの同期**: → Stage Aの実装時の判明事項で
  解消済み。`shell::execute`は`lcd.rs`のフレームループから同期的に
  呼ばれるだけで、別コンテキストからの呼び出しは無かった。
  `RefCell`/キュー化はどちらも不要だった
- **複数デバイス分のRAM**: 実装時に`core::mem::size_of`での実測は
  行っていない（**未確認のまま**）。`UsbKeyboard`/`UsbMassStorage`は
  どちらも固定長フィールドのみ（`[u8; 6]`程度のバッファ、`u8`/`u16`/`bool`
  少数）で構成されており大きくはない見込みだが、`registry::SLOT_COUNT`
  （9）× `DeviceKind`（大きい方の列挙子でサイズが決まる）のスタック/
  静的領域使用量は実機ビルドのメモリマップで確認していない。次の
  実機確認時にあわせて見ておく

## モジュール構成（実際）

- `src/usb.rs`: モジュールdocを5層構造に更新した（`hcd`→`protocol`→
  クラスドライバ（`hid_keyboard`/`hub`/`msc`）→`registry`）。
  `connect_keyboard`/`connect_keyboard_through_hub`は削除し、
  `registry::UsbHost::rescan`に統合した。`pub use`は実際に外部
  （`shell.rs`/`lcd.rs`）から名指しで参照される型・関数だけに絞った
  （`Hub`/`HubDescriptor`/`UsbKeyboard`/`UsbMassStorage`/
  `ROOT_DEVICE_ADDRESS`/`enumerate_device`/`find_hid_keyboard`/
  `find_msc_interface`は、レジストリ経由の呼び出しに閉じ込められた
  結果、外部から直接名指しする必要が無くなったため非公開のまま）
- `src/usb/registry.rs`（新規）: `UsbHost`（`last_probe`/`hub`/
  `hub_summary`/`slots: [Option<Slot>; 9]`を保持）、`DeviceKind`
  （`Keyboard`/`MassStorage`）、`DeviceSummary`（VID/PID/class/
  インターフェース数/config bytesの表示用スナップショット）、
  `Location`（`Direct`/`HubPort(u8)`）、`rescan`/`attach_hub`/
  `attach_class_driver`（デバイス種別ごとの振り分けロジック）。空きポートの
  背景走査は一時的な制御転送失敗を次周期へ無音で繰り延べ、3回連続の失敗時だけ
  停止する。`hub.rs`がchannel/FIFO復旧とEP0再同期を行うため、通常は全バスの
  `rescan`を必要としない
- `src/usb/hub.rs`: `find_connected_port`（1ポート版）と`debounce_port`
  （private）を削除し、`Hub::debounce_connected_port(port) ->
  Option<bool>`（1ポート分の接続確認+デバウンス、状態を持たない）に
  一本化した。`registry.rs`がこれをポートごとに呼ぶ
- `src/usb/protocol.rs`: `DOWNSTREAM_DEVICE_ADDRESS`定数を削除し、
  `downstream_address(port: u8) -> u8`関数に置き換えた
- `src/usb/hid_keyboard.rs`・`src/usb/msc.rs`: クラスドライバとしての
  ロジックは変更していない。`hid_keyboard.rs`から使われなくなった
  `UsbKeyboard::is_connected`（ルートポート単体の生存確認、Stage Aで
  `UsbHost::root_disconnected`に一本化されたため不要になった）と
  `HidKeyboardInterface::interval`（表示用途以外で未使用だったフィールド）
  を削除した。`msc.rs`の`MscInterface::interface_number`も同じ理由で削除
- `src/app.rs`: `run`が`usb::UsbHost`を1つ所有し、
  `poll_keyboards`で全キーボードスロットをラウンドロビンポーリングする。
  `shell::execute`へ`&mut usb_host`を渡す
- `src/shell.rs`: `usbinfo`/`usbhub`/`usbmsc`/`usbread`/`usbmbr`が
  `UsbHost`のレジストリを読み取り専用で覗く実装に置き換わった。
  唯一バスを新規に叩く`usbrescan`コマンドを新設した。共通の表示ヘルパー
  として`report_last_probe`/`report_usb_state`/`location_text`/
  `device_summary_text`/`device_kind_text`を追加した
