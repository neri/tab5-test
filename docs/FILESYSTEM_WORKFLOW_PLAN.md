## 決定ゲート: 書き込める媒体を増やすか

**この判断を先に行う。** (3)の設計も、(1)の`mkdir`をどこで使えるようにするかも、
これで変わる。

現状、VFSから書き込める唯一のボリュームは`/tmp`である。8 MiBのPSRAM上にあり、
リセットと電源断で消える。したがって「ネットワークで受信したファイルを保存する」を
現状の方針のまま実装すると、**8 MiBを超えるファイルは保存できず、保存しても
再起動すると消える**。

選択肢は3つある。

| 選択肢 | 内容 | 影響 |
| --- | --- | --- |
| A | 現状維持。保存先は`/tmp`だけ | 実装はこの計画のまま。受信ファイルは揮発し、8 MiB未満に限られる。「PCへ持っていく」用途には使えない |
| B | SDカードへの書き込みを解禁する | 保存が実用になる。[`FILESYSTEM_PLAN.md`](FILESYSTEM_PLAN.md)が全Stageで固定した方針の変更であり、**媒体ごとのflush保証と障害時挙動の実装・受入が前提**（同計画「書き込みと整合性の方針」）。誤ったLBAへの書き込みは利用者のデータを壊す |
| C | 本体Flashの`storage`領域を使う | 12 MiB、不揮発。Flash専用FS（LittleFS相当）の選定・実装が別途必要で、[`FILESYSTEM_PLAN.md`](FILESYSTEM_PLAN.md)は今回のスコープ外としている |

前計画がSD/USBを読み取り専用に固定した理由は、書き込みの受入試験をしていない
段階で利用者の媒体を壊す危険を避けるためであって、原理的な禁止ではない。
Bを選ぶ場合、この計画のStage 0として**SD書き込みの受入**を先に置く。

Aを選んでも(1)と(2)は完全に価値があり、(3)も「受信して確認する」用途には足りる。
**推奨はA**である。まずAで3機能を通し、保存の使い勝手が実際に足りないと分かってから
Bを別計画として検討するほうが、受入試験の目的がはっきりする。

## 1. カレントディレクトリ

### カレントディレクトリはVFSに置かない

VFSはカレントディレクトリを持たない。持つのは**シェル**で、相対パスは
シェルが絶対パスへ直してからVFSへ渡す。

前計画のStage 2で「相対パスは受け付けない。カレントディレクトリが無いので
基準が無い」と決めた。その決定はそのまま維持する。カレントディレクトリは
利用者インタフェースの概念であって、ファイルシステムの性質ではない。VFSへ入れると:

- VFSに入る全てのパスが正規化済みの絶対パスである、という不変条件が消える。
  現在この不変条件のおかげで、マウント解決も名前比較もFATドライバへの受け渡しも
  「もう正規化されている」ことを前提に書けている
- 利用者が複数になったとき（シェル、ネットワーク保存、将来のアプリ）、
  誰のカレントディレクトリなのかを決めなければならなくなる

シェル側で解決するなら、`path::normalize`が既に`..`と`.`を畳むので、
`cwd`と引数を`/`で連結して正規化するだけで済む。新しい解決規則は要らない。

### 必要になるVFS側の追加

| 追加 | 用途 |
| --- | --- |
| `Vfs::metadata(path) -> EntryKind + size` | `cd`が「そこはディレクトリか」を確かめる。`list`で代用すると全エントリを走査することになる |
| `Vfs::create_dir(path)` | `mkdir`。FATは`hadris-fat`の`create_dir`、exFATは読み取り専用なので拒否 |

`Vfs`の公開APIに`mkdir`が加わるのは前計画の「初期範囲外」からの拡張である。
`rename`／`remove`／`truncate`は**この計画でも範囲外**とする（下記Stage 3を参照）。

### 開始時に決めたこと

実装開始時に下記のとおり決めた。理由と現在の挙動は
[`CONSOLE_SHELL.md`](CONSOLE_SHELL.md)の「カレントディレクトリとパス引数の解決」に
ある。

| 論点 | 決定 |
| --- | --- |
| `cd`の対象が消えたとき | **文字列として保持したまま**。以後のコマンドが`NotMounted`で失敗し、同じ場所にマウントし直せばまた通る。`umount`も媒体チェックもシェルの状態を触らない |
| `mkdir`が親を作るか | **最後の要素だけ作る**。ファイル作成と同じ規則。`mkdir -p`相当は持たない |
| `cd`の引数なし | **`/`へ戻す**。ホームディレクトリの概念が無く、`/`は何がマウントされていても必ずある |
| プロンプト表示 | **出さない**。`Console`の`PROMPT`は固定長で、`MAX_LINE`もカーソル左端も行編集もその長さに依存する。現在地は`pwd`で見る |

### 実装中に決めたこと: `ls`を実物に寄せる

計画に無かった項目である。従来の`ls`は種別・サイズ・日時を毎行付け、媒体上の
並び順のまま出していた。既定を**名前のみ・名前順・桁詰め**に変え、詳細表示は
`-l`、`.`と`..`は`-a`へ移した。決めたことは下記のとおり。

| 論点 | 決定 |
| --- | --- |
| レイアウト | 実物の`ls`と同じ桁詰め。**列幅は列ごと**、名前は**列を上から下へ**。1行は104桁に収まりきらない手前まで |
| `.`と`..` | 既定で隠し、`-a`で出す |
| `N entries`行 | `-l`のときだけ |
| 並び順 | ASCIIの大文字小文字を無視し、同じなら大文字小文字で決める（FATが大文字小文字を区別しないため） |
| ツリー上のノード（`/`、`/vol`） | ボリュームと同じく名前順。片方だけマウント順にすると同じ名前で2つの動作になる |

桁詰めはホスト側で実際の`ls -C -w 104`と突き合わせて確認した（90ケース一致）。
そのとき分かったことが2つある。**列幅を全体の最長で揃えると実物と大きくずれる**
（1つ長い名前があると全列が離れる）ことと、**1行がちょうど104桁だと駄目**なこと。
後者は`Console::write_output_line`が104桁目で改行した上に行末でもう一度改行するので
空行が1行残るためで、GNU `ls`が同じ条件を`<`で持っているのと理由まで一致していた。

ソートのためエントリを全部集めてから表示する形になり、`Vfs::list`の
コールバック（名前をディレクトリバッファから借す）と噛み合わなくなったので、
`files.rs`側で名前を`String`へ複製している。

### 実装中に決めたこと: RAMディスクのマウントポイントを`/tmp`へ改名

これも計画に無かった項目である。`/ram`は媒体の名前で、`/vol`（役割の名前）と
並ぶと階層の粒度が揃わない。`/tmp`はUnixの慣習どおりで、起動ごとに
フォーマットし直しリセットで消えるという実態にも合う。

**デバイス名`ram`は変えていない。**`devices`と`blkread`が扱うのはブロック
デバイスで、実体はPSRAM上のRAMディスクである。`mount ram`が`/tmp`に乗る形になり、
`sd0p1`が`/vol/sd0p1`に乗るのと同じく名前とマウント先は一致しない。

[`FILESYSTEM_PLAN.md`](FILESYSTEM_PLAN.md)本文の`/ram`は当時の記録としてそのままに
してあり、冒頭に改名の断りを1行入れた。

### 実装中に見つかった問題: `ls /`の名前が`cd`に渡せない

計画に無かった項目である。`ls /`はマウントポイントを`file_name()`（最後の要素）で
並べていたので、`/vol/sd0p1`は`sd0p1`と表示されていた。相対パスが入ると
`cd sd0p1`は`/sd0p1`になり`NotMounted`で失敗する。**一覧が出す唯一の名前が
使えない名前**という矛盾で、カレントディレクトリを入れて初めて表面化した。

`/vol`をマウントポイントの途中の要素から合成するようにして直した。`ls /`は
`ram`と`vol`を並べ、`ls /vol`が`sd0p1`／`usb0p1`を並べる。合成ノードは下に
何かがマウントされているあいだだけ存在する（`/`だけは常にある）。
`Vfs::list`のルート専用の分岐を、この一般規則に置き換えた。

### Stage 1-1: カレントディレクトリと`cd`／`pwd`（完了、実機確認済み）

- シェルに`cwd: Path`を持たせ、引数が`/`で始まらなければ`cwd`と連結して正規化する
- `Vfs::metadata`を追加し、`cd`が対象の存在と種別を確認する
- `ls`／`cat`／`write`／`append`を相対パス対応にする。**これらのコマンド側は
  変更しない**——引数解決を1箇所（`split_argument`の後段）に置き、そこを通す
- `pwd`を追加する

完了条件: `cd /tmp` → `ls`（引数なし）で`/tmp`の中身、`cat README.TXT`が読める。
`cd ..`と`cd .`が正規化される。`cd /tmp/README.TXT`が`not a directory`で断られる。
`cd /nosuch`が失敗し、カレントディレクトリが変わらない。

### Stage 1-2: `mkdir`（完了、実機確認済み）

- `Vfs::create_dir`を追加し、FATのみ受け付ける（exFATと読み取り専用マウントは拒否）
- `mkdir <path>`を追加する

完了条件: `/tmp`にディレクトリを作り、`cd`で入り、その中に`write`でファイルを作り、
`ls`で見え、`cat`で読める。`mkdir /vol/sd0p1/X`が`read-only`で断られる。

## 2. USB抜き差しの自動マウント

### 明示マウント方針の変更点

[`FILESYSTEM_PLAN.md`](FILESYSTEM_PLAN.md)は「マウント操作は明示的に行う」と固定し、
[`FILESYSTEM.md`](FILESYSTEM.md)も「ツリーに現れるボリュームは必ず誰かが
マウントを要求した結果」と書いている。自動マウントはこれを変える。

**変えてよい理由**: あの方針の目的は、起動媒体の探索順のような判断が
「いつの間にかマウントされていた」に紛れ込むのを防ぐことだった。自動マウントは
その判断をしない。挿さっているものを見えるようにするだけである。

**変えるにあたって守ること**:

- **無効化できること**。`automount off`で完全に止まり、止めれば従来どおり
  明示マウントだけになる
- **黙って起きないこと**。マウント・アンマウントのたびにコンソールとUARTへ1行出す。
  何が起きたか分からないまま`/vol`の中身が変わるのが、元の方針が避けたかったこと
- **媒体同一性の仕組みを迂回しないこと**。自動マウントも`Vfs::mount`を通り、
  fingerprintを取り、新しいgenerationを振る。抜いて挿し直したものは
  **別のマウント**になり、古いハンドルは復活しない

### 走らせる場所

`InputManager::service`はフレームごとに走りUSBレジストリを持つが、`Vfs`を持たない。
そして**マウントはフレームループの中で走らせない**。ボリュームを開くのはバスI/Oと
FAT解析であり、数十msかかり得る。表示DMAとは独立だが、コンソールの再描画が
その間止まる。

したがって、フレームループは「USBの構成が変わった」ことだけを記録し、
実際のマウントは`app::run`のループがコマンド実行と同じ位置で行う。
シェルコマンドとしての`mount`と同じ扱いになり、新しい停止要因を作らない。

構成変化の検出には既存の`UsbHost::connection_epoch_at`と
`mass_storage_inventory`が使える。前者が進んだか、後者の並びが変わったかを見る。

### 開始時に決めること

- **何をマウントするか**。有効なMBR primary entryを全部か、読めるファイルシステムが
  載っている最初の1つか。全部にすると、Windowsが作る回復パーティションのような
  「見せても意味のないもの」も`/vol`に並ぶ
- **マウントポイント名の衝突**。`usbM`はストレージデバイスを数えた番号なので、
  2本挿しの1本目を抜くと2本目が`usb0`へ繰り上がる。このとき古い`/vol/usb0p1`が
  残っていると新しい`usb0p1`と名前が衝突する。**これはこの機能の一番厄介な点**で、
  候補は「繰り上がりを検出したら古いマウントを先に落とす」「デバイス番号を
  抜き差しで再利用しない通し番号にする」のいずれか。後者は`devices`の表示とも
  一致させる必要がある
- **取り外し時の強制アンマウント**。現状`umount`は開いているファイルがあれば
  `Busy`で断る。物理的に抜かれた場合は媒体がもう無いので`Busy`に意味がない。
  強制的に落とし、ハンドルは以後失敗させる（既にそうなる）でよいかを確認する
- **起動時の扱い**。電源投入時に既に挿さっているUSBを自動マウントするか。
  するなら、[`STORAGE.md`](STORAGE.md)の起動時USB利用可能化予算
  （connect 1,000 ms、MSC ready 4,000 ms）が起動時間に乗る
- **SDカードを対象にするか**。SDスロットには挿抜検出線が無く、挿さっているかは
  コマンドのタイムアウトでしか分からない。定期的に活性化を試すのはバスと
  ログの無駄が大きい。**当面はUSBのみとし、SDは明示マウントのままにする**のが妥当

### Stage 2-1: 取り外しの自動アンマウント

先に外す側だけを実装する。安全側であり、現状の「抜いた後もマウントが残って
操作のたびに失敗する」状態が直ちに改善する。

- USBの構成変化を検出したら、`connection_epoch`が進んだマウントを落とす
- 落としたことをコンソールとUARTへ出す

完了条件: `mount usb0p1`した状態でUSBメモリを抜くと、数秒以内に自動で
アンマウントされ`mounts`から消える。開いていたファイルハンドルは以後失敗する。
`automount off`にすると従来どおりマウントが残る。

### Stage 2-2: 挿入の自動マウント

- 新しく現れたUSBストレージのMBRを読み、対象パーティションをマウントする
- 上記「何をマウントするか」「名前の衝突」の決定に従う

完了条件: USBメモリを挿すと数秒以内に`/vol/usb0p1`が現れ、`ls`で読める。
抜いて挿し直すと**新しいgeneration**でマウントされる。2本挿して1本目を抜いたとき、
残った1本のマウントが壊れず、名前の衝突も起きない。

## 3. ネットワークで受信したファイルの保存

### 現状

- `tftpget`は`tftp::get`が返す`Vec<u8>`（最大8 MiB、ヒープ上）に全体を溜め、
  CRC-32とスループットを出して**捨てている**
- `httpget`は`http::get`が応答の先頭だけを保持し、残りは受信しながら捨てている。
  ステータスとヘッダを見るための実装であって、本文を取るためのものではない

### 溜めてから書くのではなく、届いた分から書く

現状のTFTPは「全部ヒープに溜めてから」返す。保存を足すなら、ここを
**受信しながらsinkへ渡す**形に変えるほうがよい。理由:

- ヒープ（約22 MiB）とファイルサイズが結びつかなくなる。現状の8 MiB上限は
  ヒープを守るための数字であって、プロトコルの制限ではない
- 同じsink機構でCRC-32計算も進捗表示も書き込みも扱える。今あるのは
  `progress: &mut dyn FnMut(usize)`というコールバックなので、形は既に近い
- HTTPも同じ形にすれば、本文を切り捨てずに保存できる

`tftp::get`のシグネチャを`Vec<u8>`を返す形から、`&mut dyn FnMut(&[u8]) -> bool`
のようなsinkを取る形へ変える。呼び出し側が「CRCだけ取る」「ファイルへ書く」
「両方」を選ぶ。

### VFSに流し込み用の書き込み経路が要る

sinkでファイルへ書くと、VFSの書き込みが転送のタイミング経路に入る。
TFTPは1ブロックごとのロックステップなので、書き込みが遅ければ転送が待つだけで
壊れはしない。問題は速度のほうで、**現状の`Vfs::write`を512 byteごとに呼ぶと
ファイルサイズの二乗に比例する**。

これは採用ライブラリの制限ではない。`FileWriter`は`current_cluster`と
クラスタ内オフセットを内部に持ち、同じ`FileWriter`に対して`write()`を繰り返せば
**線形**である。それがライブラリの想定する使い方である。

二乗になるのは`FileWriter::new_append`が「FATチェーンを辿って最後のクラスタを探す」
ためで、これは**構築のたび**のコストである。そして現状のVFSは`write`の呼び出しごとに
`FileWriter`を作り直す。マウントがファイルシステムを保持しない設計
（[`FILESYSTEM.md`](FILESYSTEM.md)「マウントはファイルシステムを保持しない」）の
帰結であって、ライブラリ側の都合ではない。

したがって対処は**VFSに流し込み用の書き込み経路を足す**ことである。

```text
Vfs::write_stream(devices, path, mode, |sink| { …転送… })
```

1回の呼び出しの間だけボリュームと`FileWriter`を開いたままにし、クロージャが
`sink`へ渡したバイトをそのまま流す。開き直しもチェーン走査も1回で済み、線形になる。

sink側でまとめてから`Vfs::write`を呼ぶ案（数十KiBごと）は実装が小さいが、
定数倍を下げるだけで二乗は二乗のままである。8 MiBを64 KiBごとに書けば128回の
チェーン走査になる。**採らない。**

この経路は既存の設計と矛盾しない。ハンドルがボリュームを跨いで生き残る必要が
あるのは操作と操作の**あいだ**であって、1回の操作の内側ではない。`ls`も`cat`も
既に1回の呼び出しの内側ではボリュームを開いたまま動いている。

借用の確認: クロージャはTFTPのために`&mut Stack`と`&mut Rpc`を要求するが、
これらは`Devices`とは別のオブジェクトなので同時に借りられる。

### 開始時に決めること（書き込み経路）

- **`write_stream`の失敗時**。クロージャが途中で失敗した場合、`finish`を呼んで
  そこまでを確定させるか、確定させずに終わるか。確定させないとクラスタが
  リークする（`remove`が無いので回収できない）
- **`Vfs::write`との関係**。既存の`write`を`write_stream`の上に載せ直すか、
  2つ残すか

### 開始時に決めること

- **転送が途中で失敗したときのファイル**。書きかけのファイルが残る。
  消すには`remove`が要るが、これは初期VFSの範囲外である。候補は
  「残して警告する」「`.part`のような名前で書き、成功時に改名する」（改名も範囲外）、
  「`remove`をこの計画に含める」
- **保存先の既定**。引数で指定させるか、カレントディレクトリ（機能1）に
  ファイル名で置くか
- **上書きの扱い**。既存ファイルがあるとき、`Truncate`で上書きするか断るか
- **HTTPの本文とヘッダの分離**。保存するのは本文だけであるべきだが、
  現状の`http::get`はヘッダ込みで先頭を返している

### Stage 3-1: sinkへの作り替え

- `tftp::get`をsinkを取る形に変え、`tftpget`の現状の挙動（CRC-32とスループット）を
  sink経由で再現する
- ファイルへは書かない。**この段階では外から見た挙動が変わらないことが完了条件**

完了条件: `tftpget`の出力（バイト数、CRC-32、スループット）が変更前と一致する。
8 MiBを超えるファイルが`TooLarge`ではなく受信できる。

### Stage 3-2: `Vfs::write_stream`

- 1回の呼び出しの内側でボリュームと`FileWriter`を開いたままにする経路を足す
- ネットワークとは独立に、シェルから確認できる形で先に入れる

完了条件: 数MiBのファイルを`/tmp`へ書く時間が、書き込み単位を変えても
**サイズに線形**であること（現状の`Vfs::write`繰り返しと比較して記録する）。

### Stage 3-3: ファイルへの保存

- `tftpget <host> <file> <保存先>`（構文は開始時に決める）で`write_stream`経由で書く

完了条件: 受信したファイルの内容がサーバ側と一致する（CRC-32で照合）。
`ls`でサイズと日時が出る。`cat`で読める。読み取り専用マウントへの保存が断られる。

### Stage 3-4: HTTP

- `http::get`を同じsink形式にし、ヘッダと本文を分けて本文だけ保存する

完了条件: HTTPで取得したファイルが保存でき、内容が一致する。

## 実装順の推奨

**1 → 2 → 3** の順を推奨する。

- (1)は他の2つから独立していて、かつ(3)の保存先指定を書きやすくする
- (2)のStage 2-1（自動アンマウント）は現状の不便が直ちに直るので早いほうがよい
- (3)は最も大きく、かつ冒頭の決定ゲート（書き込める媒体）の答え次第で
  価値が変わる
