## 決定ゲート: 書き込める媒体を増やすか

**この判断を先に行う。** (3)の設計も、(1)の`mkdir`をどこで使えるようにするかも、
これで変わる。

現状、VFSから書き込める唯一のボリュームは`/tmp`である。8 MiBのPSRAM上にあり、
リセットと電源断で消える。したがって「ネットワークで受信したファイルを保存する」を
現状の方針のまま実装すると、**8 MiBを超えるファイルは保存できず、保存しても
再起動すると消える**。

選択肢は3つある。

| 選択肢 | 内容 | 影響 |
| --- | --- | --- |
| A | 現状維持。保存先は`/tmp`だけ | 実装はこの計画のまま。受信ファイルは揮発し、8 MiB未満に限られる。「PCへ持っていく」用途には使えない |
| B | SDカードへの書き込みを解禁する | 保存が実用になる。[`FILESYSTEM_PLAN.md`](FILESYSTEM_PLAN.md)が全Stageで固定した方針の変更であり、**媒体ごとのflush保証と障害時挙動の実装・受入が前提**（同計画「書き込みと整合性の方針」）。誤ったLBAへの書き込みは利用者のデータを壊す |
| C | 本体Flashの`storage`領域を使う | 12 MiB、不揮発。Flash専用FS（LittleFS相当）の選定・実装が別途必要で、[`FILESYSTEM_PLAN.md`](FILESYSTEM_PLAN.md)は今回のスコープ外としている |

前計画がSD/USBを読み取り専用に固定した理由は、書き込みの受入試験をしていない
段階で利用者の媒体を壊す危険を避けるためであって、原理的な禁止ではない。
Bを選ぶ場合、この計画のStage 0として**SD書き込みの受入**を先に置く。

Aを選んでも(1)と(2)は完全に価値があり、(3)も「受信して確認する」用途には足りる。
**推奨はA**である。まずAで3機能を通し、保存の使い勝手が実際に足りないと分かってから
Bを別計画として検討するほうが、受入試験の目的がはっきりする。

## 1. カレントディレクトリ

### カレントディレクトリはVFSに置かない

VFSはカレントディレクトリを持たない。持つのは**シェル**で、相対パスは
シェルが絶対パスへ直してからVFSへ渡す。

前計画のStage 2で「相対パスは受け付けない。カレントディレクトリが無いので
基準が無い」と決めた。その決定はそのまま維持する。カレントディレクトリは
利用者インタフェースの概念であって、ファイルシステムの性質ではない。VFSへ入れると:

- VFSに入る全てのパスが正規化済みの絶対パスである、という不変条件が消える。
  現在この不変条件のおかげで、マウント解決も名前比較もFATドライバへの受け渡しも
  「もう正規化されている」ことを前提に書けている
- 利用者が複数になったとき（シェル、ネットワーク保存、将来のアプリ）、
  誰のカレントディレクトリなのかを決めなければならなくなる

シェル側で解決するなら、`path::normalize`が既に`..`と`.`を畳むので、
`cwd`と引数を`/`で連結して正規化するだけで済む。新しい解決規則は要らない。

### 必要になるVFS側の追加

| 追加 | 用途 |
| --- | --- |
| `Vfs::metadata(path) -> EntryKind + size` | `cd`が「そこはディレクトリか」を確かめる。`list`で代用すると全エントリを走査することになる |
| `Vfs::create_dir(path)` | `mkdir`。FATは`hadris-fat`の`create_dir`、exFATは読み取り専用なので拒否 |

`Vfs`の公開APIに`mkdir`が加わるのは前計画の「初期範囲外」からの拡張である。
`rename`／`remove`／`truncate`は**この計画でも範囲外**とする（下記Stage 3を参照）。

### 開始時に決めたこと

実装開始時に下記のとおり決めた。理由と現在の挙動は
[`CONSOLE_SHELL.md`](CONSOLE_SHELL.md)の「カレントディレクトリとパス引数の解決」に
ある。

| 論点 | 決定 |
| --- | --- |
| `cd`の対象が消えたとき | **文字列として保持したまま**。以後のコマンドが`NotMounted`で失敗し、同じ場所にマウントし直せばまた通る。`umount`も媒体チェックもシェルの状態を触らない |
| `mkdir`が親を作るか | **最後の要素だけ作る**。ファイル作成と同じ規則。`mkdir -p`相当は持たない |
| `cd`の引数なし | **`/`へ戻す**。ホームディレクトリの概念が無く、`/`は何がマウントされていても必ずある |
| プロンプト表示 | **出さない**。`Console`の`PROMPT`は固定長で、`MAX_LINE`もカーソル左端も行編集もその長さに依存する。現在地は`pwd`で見る |

### 実装中に決めたこと: `ls`を実物に寄せる

計画に無かった項目である。従来の`ls`は種別・サイズ・日時を毎行付け、媒体上の
並び順のまま出していた。既定を**名前のみ・名前順・桁詰め**に変え、詳細表示は
`-l`、`.`と`..`は`-a`へ移した。決めたことは下記のとおり。

| 論点 | 決定 |
| --- | --- |
| レイアウト | 実物の`ls`と同じ桁詰め。**列幅は列ごと**、名前は**列を上から下へ**。1行は104桁に収まりきらない手前まで |
| `.`と`..` | 既定で隠し、`-a`で出す |
| `N entries`行 | `-l`のときだけ |
| 並び順 | ASCIIの大文字小文字を無視し、同じなら大文字小文字で決める（FATが大文字小文字を区別しないため） |
| ツリー上のノード（`/`、`/vol`） | ボリュームと同じく名前順。片方だけマウント順にすると同じ名前で2つの動作になる |

桁詰めはホスト側で実際の`ls -C -w 104`と突き合わせて確認した（90ケース一致）。
そのとき分かったことが2つある。**列幅を全体の最長で揃えると実物と大きくずれる**
（1つ長い名前があると全列が離れる）ことと、**1行がちょうど104桁だと駄目**なこと。
後者は`Console::write_output_line`が104桁目で改行した上に行末でもう一度改行するので
空行が1行残るためで、GNU `ls`が同じ条件を`<`で持っているのと理由まで一致していた。

ソートのためエントリを全部集めてから表示する形になり、`Vfs::list`の
コールバック（名前をディレクトリバッファから借す）と噛み合わなくなったので、
`files.rs`側で名前を`String`へ複製している。

### 実装中に決めたこと: RAMディスクのマウントポイントを`/tmp`へ改名

これも計画に無かった項目である。`/ram`は媒体の名前で、`/vol`（役割の名前）と
並ぶと階層の粒度が揃わない。`/tmp`はUnixの慣習どおりで、起動ごとに
フォーマットし直しリセットで消えるという実態にも合う。

**デバイス名`ram`は変えていない。**`devices`と`blkread`が扱うのはブロック
デバイスで、実体はPSRAM上のRAMディスクである。`mount ram`が`/tmp`に乗る形になり、
`sd0p1`が`/vol/sd0p1`に乗るのと同じく名前とマウント先は一致しない。

[`FILESYSTEM_PLAN.md`](FILESYSTEM_PLAN.md)本文の`/ram`は当時の記録としてそのままに
してあり、冒頭に改名の断りを1行入れた。

### 実装中に見つかった問題: `ls /`の名前が`cd`に渡せない

計画に無かった項目である。`ls /`はマウントポイントを`file_name()`（最後の要素）で
並べていたので、`/vol/sd0p1`は`sd0p1`と表示されていた。相対パスが入ると
`cd sd0p1`は`/sd0p1`になり`NotMounted`で失敗する。**一覧が出す唯一の名前が
使えない名前**という矛盾で、カレントディレクトリを入れて初めて表面化した。

`/vol`をマウントポイントの途中の要素から合成するようにして直した。`ls /`は
`ram`と`vol`を並べ、`ls /vol`が`sd0p1`／`usb0p1`を並べる。合成ノードは下に
何かがマウントされているあいだだけ存在する（`/`だけは常にある）。
`Vfs::list`のルート専用の分岐を、この一般規則に置き換えた。

### Stage 1-1: カレントディレクトリと`cd`／`pwd`（完了、実機確認済み）

- シェルに`cwd: Path`を持たせ、引数が`/`で始まらなければ`cwd`と連結して正規化する
- `Vfs::metadata`を追加し、`cd`が対象の存在と種別を確認する
- `ls`／`cat`／`write`／`append`を相対パス対応にする。**これらのコマンド側は
  変更しない**——引数解決を1箇所（`split_argument`の後段）に置き、そこを通す
- `pwd`を追加する

完了条件: `cd /tmp` → `ls`（引数なし）で`/tmp`の中身、`cat README.TXT`が読める。
`cd ..`と`cd .`が正規化される。`cd /tmp/README.TXT`が`not a directory`で断られる。
`cd /nosuch`が失敗し、カレントディレクトリが変わらない。

### Stage 1-2: `mkdir`（完了、実機確認済み）

- `Vfs::create_dir`を追加し、FATのみ受け付ける（exFATと読み取り専用マウントは拒否）
- `mkdir <path>`を追加する

完了条件: `/tmp`にディレクトリを作り、`cd`で入り、その中に`write`でファイルを作り、
`ls`で見え、`cat`で読める。`mkdir /vol/sd0p1/X`が`read-only`で断られる。

## 2. USB抜き差しの自動マウント

### 明示マウント方針の変更点

[`FILESYSTEM_PLAN.md`](FILESYSTEM_PLAN.md)は「マウント操作は明示的に行う」と固定し、
[`FILESYSTEM.md`](FILESYSTEM.md)も「ツリーに現れるボリュームは必ず誰かが
マウントを要求した結果」と書いている。自動マウントはこれを変える。

**変えてよい理由**: あの方針の目的は、起動媒体の探索順のような判断が
「いつの間にかマウントされていた」に紛れ込むのを防ぐことだった。自動マウントは
その判断をしない。挿さっているものを見えるようにするだけである。

**変えるにあたって守ること**:

- **無効化できること**。`automount off`で完全に止まり、止めれば従来どおり
  明示マウントだけになる
- **黙って起きないこと**。マウント・アンマウントのたびにコンソールとUARTへ1行出す。
  何が起きたか分からないまま`/vol`の中身が変わるのが、元の方針が避けたかったこと
- **媒体同一性の仕組みを迂回しないこと**。自動マウントも`Vfs::mount`を通り、
  fingerprintを取り、新しいgenerationを振る。抜いて挿し直したものは
  **別のマウント**になり、古いハンドルは復活しない

### 走らせる場所

`InputManager::service`はフレームごとに走りUSBレジストリを持つが、`Vfs`を持たない。
そして**マウントはフレームループの中で走らせない**。ボリュームを開くのはバスI/Oと
FAT解析であり、数十msかかり得る。表示DMAとは独立だが、コンソールの再描画が
その間止まる。

したがって、フレームループは「USBの構成が変わった」ことだけを記録し、
実際のマウントは`app::run`のループがコマンド実行と同じ位置で行う。
シェルコマンドとしての`mount`と同じ扱いになり、新しい停止要因を作らない。

構成変化の検出には既存の`UsbHost::connection_epoch_at`と
`mass_storage_inventory`が使える。前者が進んだか、後者の並びが変わったかを見る。

### 開始時に決めたこと

実装開始時に下記のとおり決めた。現在の挙動は[`FILESYSTEM.md`](FILESYSTEM.md)の
「USBの自動マウント」にある。

| 論点 | 決定 |
| --- | --- |
| 何をマウントするか | **読めるファイルシステムが載っているMBR primary entryを全部**。載っていないentryは`Vfs::mount`がブートセクタで断るので静かに飛ばす。Windowsの回復パーティション（NTFS）はこれで自動的に除外される。1つもマウントできなければ`no readable filesystem`と1行出す |
| マウントポイント名の衝突 | **`usbM`を通し番号にした**。基本は順に増え、`STORAGE_ID_LIMIT`（16）まで進むと先頭へ戻るが、**接続中のデバイスが持っている番号は飛ばす**。1本目を抜いても2本目の番号は動かない |
| 取り外し時の強制アンマウント | **強制する**。媒体がもう無いので`Busy`に意味がない。マウントを落とし、残ったハンドルは以後失敗する（`fsverify`の`DISCONNECTED since mount`と同じ経路・同じ根拠） |
| 起動時の扱い | **する**。USBスキャン自体は`InputManager::new`が起動シーケンスで済ませているので、追加で乗るのはMBR読み出しとボリュームopenだけ。[`STORAGE.md`](STORAGE.md)の起動時予算は変わらない |
| SDカードを対象にするか | **しない**。挿抜検出線が無く、挿さっているかはコマンドのタイムアウトでしか分からない。定期的に活性化を試すのはバスとログの無駄が大きい |

### 実装中に決めたこと: `usbM`を通し番号にした

計画では「繰り上がりを検出して古いマウントを先に落とす」も候補に挙げていたが、
採らなかった。あれは1本目を抜いたときに、**触っていない2本目のマウントも一度
落ちて`/vol/usb1p1`から`/vol/usb0p1`へ付け替わり、generationも変わる**。開いて
いたファイルは失敗し、`cd`していた場所も消える。Stage 2-2の完了条件「残った
1本のマウントが壊れず」を素直には満たさない。

通し番号にすると、`usbM`の`M`は位置ではなくデバイスに付く名前になる。変更点は
レジストリ側に閉じた。

- 番号はスロット（＝バス上の位置）ごとに`ConnectionEpoch`と一緒に**予約**する。
  再スキャンは全スロットをいったん空にしてから作り直すので、その間も予約が
  残っていないと、戻ってきた同じデバイスが別番号になりマウントが全部壊れる
- ポートで接続変化のedgeが観測されていれば予約は無効になる。同じポートに挿した
  別のデバイスは新しい番号を受け取る
- `mass_storage_at`／`mass_storage_location`／`mass_storage_inventory`は
  「`n`番目」ではなく「番号`id`」で引く。`devices`の表示もこの番号を出す

`Mount`が記録する**バス上の位置**の照合はそのまま残した。意味が変わり、「同じ番号が
別の位置のデバイスを指すようになった」ではなく「このデバイスが別のポートへ
挿し替えられた」を捕まえる検査になった。

### 実装中に決めたこと: 応答しないだけのデバイスは落とさない

`Vfs::prune_disconnected`が見るのは`ConnectionEpoch`が進んだかどうかだけで、
「そのデバイスが今いるか」は見ない。再スキャンが一時的にデバイスを取りこぼした
だけの状態でマウントを落とすと、[`FILESYSTEM.md`](FILESYSTEM.md)の
「rescanを跨いでもマウントは生き残る」と矛盾する。抜かれたことを**観測した**
edgeだけを根拠にする。

その結果、取りこぼしから復帰したデバイスは自動マウントから見ると「新しく現れた」
ように見えるので、既にマウント済みのパーティションは飛ばす判定を入れた。

### 実装中に決めたこと: コンソールの入力途中の行を退避する

計画に無かった項目である。`Console::write_output_line`は現在行の0桁目から
書き始めるので、入力途中の行に出すとプロンプトも打ちかけのコマンドも消える。
コマンドの出力は常にEnterが入力行を消費した直後に書かれるので今まで問題に
ならなかったが、自動マウントは利用者が入力している最中に報告する。

`Console::take_input_line`／`restore_input_line`を足した。呼ぶのは最初の1行を
出す直前で、報告することが何も無い突き合わせ（定期再スキャンのたびに起きる）
ではカーソルを動かさない。詳細は[`CONSOLE_SHELL.md`](CONSOLE_SHELL.md)。

### 実装中に見つかった問題: ハンドルの状態がコンソールから見えない

実機確認で判明した項目である。Stage 2-1の完了条件に「開いていたファイル
ハンドルは以後失敗する」があるが、`cat`をはじめ既存のコマンドは開いたものを
戻る前に必ず閉じるので、**ドライブを抜く瞬間にハンドルが開いている状態を
コンソールから作れなかった**。条件が観測不能だった。

`Vfs::describe`（開ファイル表を公開せずに1つ分を写して返す）と、それを使う
`fsopen`／`fsread`／`fsclose`を足した。`fsopen`はコマンドを跨いでハンドルを
保持し、一覧に`live`／`stale`を出す。判定は`Vfs::read`が媒体に触れる前に行う
のと同じ検査（マウント点にボリュームがあり、それがハンドルを開いたときと同じ
generationか）なので、一覧と次の読み出しの答えが食い違いません。

保持は**読み取り専用**に限りました。`Truncate`のハンドルをコマンドを跨いで
保持すると、利用者が放置している間ずっと中途半端に適用された状態が残ります。
この経路の目的はハンドルが失効するのを見ることであって、書くことではありません。

### 実装中に見つかった問題: 接続直後は読めない

実機確認で判明した項目である。「exFATの自動マウントが不安定」という形で
現れたが、**exFATもメディアの個体差も原因ではなかった**。

デバイスは列挙に答えた時点で`slots`にbindされ、そこで`topology_epoch`が進む。
自動マウントはその同じフレームでMBRを読みに行くが、`UsbMscBlockDevice::probe`は
TEST UNIT READYを1回撃って駄目なら`NotReady`で戻る。logical unitが立ち上がる
前に聞いてしまうと`with_device`が`None`を返し、当初の実装はそれを
`no usable partition table`として報告した上、`offered`を先に立てていたので
**二度と試さなかった**。

このプロジェクトは実機がこれに数秒かかることを既に知っている。起動シーケンスの
ready待ちは`BOOT_MASS_STORAGE_READY_MS = 4,000 ms`で、[`STORAGE.md`](STORAGE.md)に
実測の経緯がある。同じ問いを別のタイミングで聞いているだけなので、同じ数字を使う。

exFATに見えたのは相関である。exFATでフォーマットされているのは大容量の媒体で、
内部初期化が長いのも大容量の媒体だから、競争に負けるのがそちらに偏る。
（副次的に`ExFatVolume::open`は`FatVolume::open`より媒体を多く読むので、
マウント時のopen自体も失敗しやすい側にある。）

対処:

- 開けなかったデバイスは`pending`に入れ、250 msおきに聞き直す。budgetは
  デバイスごとに4,000 msで、使い切ったら`did not become readable`と1行出す
- 再試行の間`topology_epoch`は動かないので、`service`は「構成が動いた」か
  「`pending`があって再試行の時刻になった」かのどちらかで走るようにした
- `None`（開けなかった）と`Some(Err(_))`（開けたがLBA 0が読めなかった）と
  `Some(Ok(_))`（読めたが使えるパーティション表が無い）を区別した。当初は
  3つとも同じ`no usable partition table`になっていて、**メッセージ自体が
  原因を隠していた**

### 実装中に見つかった問題: 転送の一時失敗を最終回答にしていた

上の修正では足りなかった。実機のログ:

```text
USB: mass storage attached on hub port 0x00000001
USB: packet timed out waiting for channel halt
USB BOT: bulk IN timed out during data IN
USB BOT: reset recovery complete
automount: usb1p1: device not present
automount: mounted usb1p2 on /vol/usb1p2
```

`automount: usb1p1: ...`（`p1`付き）はパーティションごとの失敗行なので、
**デバイスレベルの`mbr::inspect`は成功している**（p1・p2の両方が表から読めている）。
つまりready待ちの競争ではない。p1のマウント中にbulk INがタイムアウトし、BOTの
reset recoveryが走り、その最中に`UsbMscBlockDevice::probe`が失敗して
`DeviceNotPresent`になった。recoveryが済んだ後のp2は成功している。

`Vfs::mount`はfingerprint、ブートセクタ読み出し、ボリュームopenでそれぞれ
デバイスを解決し直すので、そのどれもが失敗中の転送に当たり得る。当初の実装は
それをp1の最終回答として報告し、`pending`からも外していた。

対処は失敗の分類である。`worth_retrying`が「答えが取れていない」
（`device not present`／`not ready`／`device error`／`temporarily unavailable`）と
「答えである」（読めるFSが無い、媒体が入れ替わった）を分け、前者は同じbudgetの
中で聞き直す。答えたentryはマウントされたまま残るので、再試行に残るのは
答えなかったentryだけ。

**残っている非効率**（今回は直していない）: `attach_device`はデバイスの
パーティション表を読んでから、`files::attach`が同じ表をentryごとに読み直す。
さらに`Vfs::mount`が1 entryにつき`probe`（TEST UNIT READY＋READ CAPACITY(10)）を
3回行う。2パーティションの媒体では接続直後の数百msに16以上のコマンドが集中し、
**まさに転送が不安定な瞬間に不安定な量の通信をしている**。読み直しを1回省くのは
小さな変更だが、`Vfs::mount`側の3回はVFSの設計（マウントはファイルシステムを
保持しない）の帰結なので、別途判断が要る。

### Stage 2-1: 取り外しの自動アンマウント（完了、実機確認済み）

- USBの構成変化を検出したら、`connection_epoch`が進んだマウントを落とす
  （`Vfs::prune_disconnected`）
- 落としたことをコンソールとUARTへ出す

完了条件: `mount usb0p1`した状態でUSBメモリを抜くと、数秒以内に自動で
アンマウントされ`mounts`から消える。抜く前に`fsopen`で開いておいたハンドルが
`fsopen`の一覧で`stale`になり、`fsread`が`handle no longer valid`で失敗する。
`automount off`にすると従来どおりマウントが残る。

### Stage 2-2: 挿入の自動マウント（完了、実機確認済み）

- 新しく現れたUSBストレージのMBRを読み、対象パーティションをマウントする
  （`src/app/automount.rs`）
- 上記「開始時に決めたこと」の表に従う

完了条件: USBメモリを挿すと数秒以内に`/vol/usb0p1`が現れ、`ls`で読める。
抜いて挿し直すと**新しいgeneration**でマウントされる。2本挿して1本目を抜いたとき、
残った1本のマウントが壊れず、名前の衝突も起きない。

## 3. ネットワークで受信したファイルの保存

### 現状

- `tftpget`は`tftp::get`が返す`Vec<u8>`（最大8 MiB、ヒープ上）に全体を溜め、
  CRC-32とスループットを出して**捨てている**
- `httpget`は`http::get`が応答の先頭だけを保持し、残りは受信しながら捨てている。
  ステータスとヘッダを見るための実装であって、本文を取るためのものではない

### 溜めてから書くのではなく、届いた分から書く

現状のTFTPは「全部ヒープに溜めてから」返す。保存を足すなら、ここを
**受信しながらsinkへ渡す**形に変えるほうがよい。理由:

- ヒープ（約22 MiB）とファイルサイズが結びつかなくなる。現状の8 MiB上限は
  ヒープを守るための数字であって、プロトコルの制限ではない
- 同じsink機構でCRC-32計算も進捗表示も書き込みも扱える。今あるのは
  `progress: &mut dyn FnMut(usize)`というコールバックなので、形は既に近い
- HTTPも同じ形にすれば、本文を切り捨てずに保存できる

`tftp::get`のシグネチャを`Vec<u8>`を返す形から、`&mut dyn FnMut(&[u8]) -> bool`
のようなsinkを取る形へ変える。呼び出し側が「CRCだけ取る」「ファイルへ書く」
「両方」を選ぶ。

### VFSに流し込み用の書き込み経路が要る

sinkでファイルへ書くと、VFSの書き込みが転送のタイミング経路に入る。
TFTPは1ブロックごとのロックステップなので、書き込みが遅ければ転送が待つだけで
壊れはしない。問題は速度のほうで、**現状の`Vfs::write`を512 byteごとに呼ぶと
ファイルサイズの二乗に比例する**。

これは採用ライブラリの制限ではない。`FileWriter`は`current_cluster`と
クラスタ内オフセットを内部に持ち、同じ`FileWriter`に対して`write()`を繰り返せば
**線形**である。それがライブラリの想定する使い方である。

二乗になるのは`FileWriter::new_append`が「FATチェーンを辿って最後のクラスタを探す」
ためで、これは**構築のたび**のコストである。そして現状のVFSは`write`の呼び出しごとに
`FileWriter`を作り直す。マウントがファイルシステムを保持しない設計
（[`FILESYSTEM.md`](FILESYSTEM.md)「マウントはファイルシステムを保持しない」）の
帰結であって、ライブラリ側の都合ではない。

したがって対処は**VFSに流し込み用の書き込み経路を足す**ことである。

```text
Vfs::write_stream(devices, path, mode, |sink| { …転送… })
```

1回の呼び出しの間だけボリュームと`FileWriter`を開いたままにし、クロージャが
`sink`へ渡したバイトをそのまま流す。開き直しもチェーン走査も1回で済み、線形になる。

sink側でまとめてから`Vfs::write`を呼ぶ案（数十KiBごと）は実装が小さいが、
定数倍を下げるだけで二乗は二乗のままである。8 MiBを64 KiBごとに書けば128回の
チェーン走査になる。**採らない。**

この経路は既存の設計と矛盾しない。ハンドルがボリュームを跨いで生き残る必要が
あるのは操作と操作の**あいだ**であって、1回の操作の内側ではない。`ls`も`cat`も
既に1回の呼び出しの内側ではボリュームを開いたまま動いている。

借用の確認: クロージャはTFTPのために`&mut Stack`と`&mut Rpc`を要求するが、
これらは`Devices`とは別のオブジェクトなので同時に借りられる。

### 開始時に決めたこと（書き込み経路）

| 論点 | 決定 |
| --- | --- |
| `write_stream`の失敗時 | **届いた分を確定させる**（`finish`まで呼ぶ）。確定させないと、どのディレクトリエントリからも辿れないクラスタが媒体上に残り、辿れない以上取り戻せない。確定させておけば書きかけを見ることも削除して容量を戻すこともできる。止まった理由は`StreamWrite::interrupted`で返す |
| `Vfs::write`との関係 | **2つ残す**。`write`はハンドルの位置に書くもの、`write_stream`はハンドルを持たない1回の操作で、形が違う。`write`を`write_stream`の上に載せ直すと`write_stream`側がハンドルのオフセットを扱うことになり、避けたかった`FileWriter`の作り直しが戻ってくる |

### 開始時に決めたこと

| 論点 | 決定 |
| --- | --- |
| 転送が途中で失敗したときのファイル | **`remove`と`rename`の両方を実装し、`.part`方式を採る**。一時名で書き、成功したら改名、失敗したら削除する。**ツリーに現れたファイルは完全**という保証が得られる。`hadris-fat`に`delete`と`rename`があるので、FATの操作を自前で書く必要はない |
| 保存先の既定 | **常にカレントディレクトリ**へ、リモートのファイル名で置く |
| 上書きの扱い | **`Truncate`で上書き**。失敗した転送をやり直すのが一番ありがちな使い方で、断ると同じ名前が使えなくなる |
| HTTPの本文とヘッダの分離 | 本文だけを保存する（Stage 3-4） |

`rename`／`remove`は[`FILESYSTEM.md`](FILESYSTEM.md)の「未対応」から外れた。
`truncate`は引き続き範囲外である（`Truncate`で開き直す置き換えはできる）。

### Stage 3-1: sinkへの作り替え（完了、実機確認済み）

- `tftp::get`を`&mut dyn FnMut(&[u8]) -> bool`を取る形に変え、返すのは
  転送byte数だけにした。`MAX_FILE_BYTES`（8 MiB）と`Error::TooLarge`は削除
- CRC-32は`Crc32`（`new`／`update`／`finish`）で流しながら計算する。ファイル
  全体が同時に手元にある瞬間がもう無いため
- 未見のブロックだけをsinkへ渡す。ACKが失われた再送はACKし直すが渡さない
- ファイルへは書かない。**この段階では外から見た挙動が変わらないことが完了条件**

完了条件: `tftpget`の出力（バイト数、CRC-32、スループット）が変更前と一致する。
8 MiBを超えるファイルが`TooLarge`ではなく受信できる。

### Stage 3-2: `Vfs::write_stream`（完了、実機確認済み）

- 1回の呼び出しの内側でボリュームと`FileWriter`を開いたままにする経路を足した
- あわせて`Vfs::remove_file`／`remove_dir`／`rename`と、シェルの`rm`／`rmdir`／
  `mv`を入れた（上記「開始時に決めたこと」の`.part`方式に要る）
- 計測用に`fill <path> <KiB> [chunk] [repeat]`を入れた。`repeat`が旧経路

完了条件: 数MiBのファイルを`/tmp`へ書く時間が、書き込み単位を変えても
**サイズに線形**であること（`fill`の既定と`repeat`を同じ引数で比較して記録する）。

実機での結果（`/tmp`、8 MiB FAT16）:

| 経路 | サイズを倍にする | chunkを4分の1にする |
| --- | --- | --- |
| `write_stream` | 約2倍 | ほとんど変わらない |
| `write`の繰り返し（`repeat`） | 約2倍（128 KiB→256 KiB） | 呼び出し回数に比例 |

絶対値は1点だけ取れている。

```text
> fill e.bin 256 512 repeat
write x N: 262144 bytes in 668 ms, chunk 512
```

**旧経路で256 KiB・512 byte刻みが668 ms、約392 KiB/s。**（同条件の`write_stream`側の
絶対値は記録できていない。）

### 実測で否定されたこと: 旧経路は二乗ではなかった

この計画は「現状の`Vfs::write`を512 byteごとに呼ぶと**ファイルサイズの二乗に
比例する**」と書き、`FileWriter::new_append`のFATチェーン走査を根拠にしていた。
**実測では二乗にならない。** 128 KiBと256 KiBで所要時間は約2倍、つまり線形である。

理由は、1回あたりのコストのうちチェーン走査が支配的ではないこと。`Vfs::write`は
呼び出しごとにボリュームを開き、ディレクトリを辿り、writerを作り、エントリを
確定し、syncする。8 MiBのボリュームで扱うクラスタ数では、この固定部分が走査を
覆い隠す。`n^2`の項は理屈としては存在するが、この規模では見えない。

**`write_stream`の値は変わらない。** 省いているのはその固定コストで、実用上の
差は**書き込み単位に依存しないこと**として出る。ネットワークからの流し込みは
1ブロック512 byteで届くので、旧経路ではその粒度がそのままコストになる。

### ついでに分かったこと: 旧経路でもTFTPには間に合っていた

上の392 KiB/sは、TFTPの実測スループット111 KiB/s（[`NETWORK.md`](NETWORK.md)）を
上回っている。**この計画が想定した規模では、旧経路のまま書いても転送の
ボトルネックにはならなかった**ということである。二乗の予測が外れた以上、
`write_stream`を入れる緊急性も想定より低かった。

それでも入れたままにする理由は速度ではなく形である。1回の操作の内側で
ボリュームを1回開くのは`ls`や`cat`と同じ扱いで、書き込み単位もファイルサイズも
コストに効かなくなるので、**書き込み経路が性能の考慮事項でなくなる**。
将来もっと速い転送（HTTPは既に827 KiB/s）や大きなファイルを足すときに、
ここを測り直さなくて済む。

計画本文の「二乗」という記述は当時の予測であり、現状の説明は
[`FILESYSTEM.md`](FILESYSTEM.md)を優先すること。

### Stage 3-3: ファイルへの保存（完了、実機確認済み）

- `tftpget <host> <file>`がカレントディレクトリへ、リモート名の最後の要素で保存する
- `Vfs::write_stream`1回で転送全体を包む
- `<名前>.part`へ書き、完了してから改名する。失敗したら`.part`を削除する
- 書き込みの失敗は、全byteが届いていても転送の失敗として扱う
- 保存先が書けない場合は**ネットワークに触る前に**断る

完了条件: 受信したファイルの内容がサーバ側と一致する（CRC-32で照合）。
`ls`でサイズと日時が出る。`cat`で読める。読み取り専用マウントへの保存が断られる。

試験用のTFTPサーバは`~/tftp-test/`にある（`README.md`に起動コマンドと4つの
ファイルの期待CRC-32）。最初に用意したときTFTPルートをセッション用の
スクラッチパッドに置いたため消えており、作り直した。

### 実装中に見つかった問題: `lookup`の「無い」は`Err`だった

`write_stream`が`lookup`の戻り値を取り違えていた。`lookup`はパスの要素が
見つからないとき`Err(FsError::NotFound)`を返し、`Ok(None)`は**パスがボリュームの
ルートのとき**だけである。`Ok(None)`を「無い」と読んでそこに`create`を置いたので、
`match lookup(..)?`の`?`が手前で`NotFound`を伝播させ、**まだ存在しないファイルへの
書き込みが必ず失敗**していた。`fill`が`no such file or directory`で何もできない。

すぐ上の`Vfs::open`は`Err(FsError::NotFound) if mode.writable()`で正しく受けている。
同じ形に直し、`lookup`に2つの答えの違いをdoc commentとして書いた。署名
（`Result<Option<_>>`）だけを見ると取り違える形なので。

### 実装中に決めたこと: 同一ボリュームの判定を書き込み可否より先に行う

`Vfs::rename`は当初、両側について「マウントが書けるか」を先に見ていた。書ける
ボリュームが`/tmp`しかない以上、**ボリュームを跨ぐ移動はすべて`read-only`と
報告される**ことになり、本当の理由（跨げない）が隠れる。判定順を入れ替えた。
同一ボリュームだと分かれば書き込み可否の判定も1回で済む。

### Stage 3-4: HTTP（完了、実機確認済み）

- `http::get`を同じsink形式にした。ヘッダの終わりの空行で切り分け、ヘッダは
  保持し（`MAX_HEADER_BYTES` = 4 KiB）、**本文だけ**をsinkへ渡す
- 空行は2回の読み出しにまたがり得るので、走査は溜めたバッファに対して行う
  （前回の末尾3 byteから探し直す）
- ステータスコードは`Response::status`で報告するだけで、この層は判断しない
- `httpget`もカレントディレクトリへ、パスの最後の要素で保存する。クエリ文字列は
  名前から外す
- **パスが`/`または`/`で終わる場合は保存しない**（名前にするものが無い）。
  元からのTCP疎通確認の使い方がそのまま残る
- **2xx以外は保存しない**。エラーページが利用者の求めた名前でツリーに残るのを
  避けるため

完了条件: HTTPで取得したファイルが保存でき、内容が一致する。

### 実装中に決めたこと: `httpget`は名前が作れないときだけ保存しない

`tftpget`は常に保存する。リモート名は必ずファイルを指すからである。HTTPは
違い、`/`や`/`で終わるパスは正当だが名前にするものが無い。「常にカレント
ディレクトリへ保存」という決定は**どこへ**の決定であって**するかどうか**の
決定ではないと読み、名前が作れないときは従来どおりヘッダを表示して本文を
捨てることにした。`httpget example.com`が壊れない。

## 実装順の推奨

**1 → 2 → 3** の順を推奨する。

- (1)は他の2つから独立していて、かつ(3)の保存先指定を書きやすくする
- (2)のStage 2-1（自動アンマウント）は現状の不便が直ちに直るので早いほうがよい
- (3)は最も大きく、かつ冒頭の決定ゲート（書き込める媒体）の答え次第で
  価値が変わる
